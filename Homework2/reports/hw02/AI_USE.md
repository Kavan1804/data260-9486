# AI Use

1. I used an AI assistant to help organize the starter files, implement the FastAPI CRUD/search
   routes, improve responsive HTML/CSS/JavaScript, refactor the supplied graph into LangGraph
   nodes and conditional routing, write the Part 4 experiment/verification scripts, and generate
   the final report. I reviewed and ran the code myself, and required all Part 4 numbers to come
   from real qwen3:4b runs rather than any placeholder data.
2. The AI-produced `raw/schema_runs.json`, `raw/ceiling_comparison.json`, and
   `raw/adversarial_runs.json` from an earlier pass were generated by a `FakeModel` fixture with
   sub-millisecond latencies (e.g. 3.2 ms), not the real qwen3:4b model, even though `METRICS.md`
   already flagged this. Separately, `src/model_client.py`'s `generate_json` called Ollama's
   `/api/generate` with `format=json` but without `think=False`; qwen3:4b is a thinking model, so
   Ollama put the JSON answer in an unused `thinking` field and left `response` empty, causing
   `json.loads("")` to fail on every real call.
3. I detected the fixture issue by inspecting the raw JSON files and an existing screenshot of
   them, which showed millisecond-scale latencies impossible for a live LLM call. I detected the
   `model_client.py` bug by making one real call directly against the Ollama API and printing the
   full response payload, which showed the JSON sitting in `thinking` instead of `response`.
4. I added `"think": False` to the Ollama request (matching the same setting already used in
   `Homework1/src/model_client.py`), verified a single real call succeeded, then reran all 75
   experiment calls (30 schema + 20+20 ceiling + 5 adversarial) against the real local qwen3:4b
   model and rebuilt `METRICS.md`, `RUN_LOG.txt`, and the report tables from those real results
   instead of the fixture data.
